# 監査基準

## 分類

| 判定 | 使用条件 | 例 |
| --- | --- | --- |
| 維持 | 現在も具体的な失敗、安全問題、プロジェクト固有の誤りを防ぐ | 破壊的操作の対象確認、非標準の検証コマンド |
| 圧縮 | 目的は有効だが、反復や説明が多い | 同じ禁止事項を一文にまとめる |
| 移動 | 有効だが一部タスクだけで必要 | リリース手順を常時ルールからSkillへ移す |
| 更新 | 目的は有効だが、API、ツール名、パス、能力前提が古い | 廃止されたコマンドや探索場所を置き換える |
| 統合 | 同じ目的のコピーが複数あり、独立保守する理由がない | Claude/Codex用の同一Skillを共有本体へ寄せる |
| 削除 | 防ぐ失敗が特定できない、コードから自明、現在は逆効果 | 単純作業にも毎回詳細計画を要求する |

## 証拠の優先順位

1. 現在のユーザー要求、組織ポリシー、安全要件
2. 実行可能なテスト、失敗ログ、実際のエージェント挙動
3. 現在のコード、設定、リポジトリ履歴
4. 現在の公式仕様・公式ドキュメント
5. チーム内で繰り返された具体的な失敗
6. 推測、好み、古い一般論

日付、長さ、モデル世代だけでは変更根拠にしない。ルールを残す場合も、削る場合も、上位の証拠に結び付ける。

## 陳腐化シグナル

- 存在しないツール、モデル、サブエージェント、パス、APIを前提にする。
- 現在の公式仕様と矛盾する。
- 同じ内容が常時ルール、Skill、commandに重複する。
- 低リスクな一段階作業にも、複数文書、承認待ち、詳細な進捗更新を要求する。
- 作業開始を完了として記録するなど、記録と現実が一致しない。
- 「必ず」「すべて」「絶対」が多いが、例外条件や防ぐ失敗がない。
- Skillのdescriptionが広すぎ、通常タスクでも発動する。
- 本文が一般的なAI能力や標準的な開発常識を長く説明する。
- 製品ごとのコピーが同じ内容で、差分管理の理由がない。

## 維持すべきシグナル

- 認証情報、個人情報、破壊的操作、外部公開に関する境界である。
- プロジェクト固有のアーキテクチャや、誤るとデータを壊す制約である。
- 標準から外れたビルド、テスト、デプロイ手順である。
- 実際に繰り返された失敗を、低い運用コストで防いでいる。
- 法務、コンプライアンス、組織ポリシーに由来する。

## 常時ルールとSkillの境界

常時ルールへ残す:

- ほぼ全タスクで必要なプロジェクト固有の事実
- 常に守る安全・権限・リポジトリ作法
- エージェントがコードから推測しにくい最小限の検証コマンド

Skillへ移す:

- 特定の種類の作業だけで使う手順、チェックリスト、テンプレート
- 長い参考情報、製品別のバリエーション
- 利用者が明示的に開始できる反復ワークフロー

決定論的な仕組みへ移す:

- 毎回必ず同じ判定をする形式検証
- フォーマット、schema、lint、安全な禁止操作
- AIの判断を必要としない自動化

## 発動評価例

発動すべき依頼:

- 「古くなったSkillを整理して」
- 「AGENTS.mdが過剰なので現在のCodex向けに見直して」
- 「ClaudeとCodexの重複した指示を一本化して」
- 「以前の弱いモデル向けルールがまだ必要か監査して」

発動すべきでない依頼:

- 「このReactコンポーネントをレビューして」
- 「依存パッケージを更新して」
- 「READMEの誤字を直して」
- 「このSQLを高速化して」
